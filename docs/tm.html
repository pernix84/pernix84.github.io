Case study · TM

How TM is built.

TM is a transit-management product: routes and stops on a map, vehicles and drivers, trips and where every vehicle is right now. It is the real workload on the MRZ platform, built the way a team would build it — contracts first, data owned by one service, every shortcut written down.

Why this architecture

What it is chosen for

  • Clear ownership: a service owns its data, and nobody else reads its database
  • Two services, not ten — a new one only where data and release pace really differ
  • One entry point per kind of client, so the domain services never talk to each other
  • Events for what others react to; synchronous calls only from the entry point, each time-boxed

What it costs, accepted openly

  • More moving parts than a monolith: a broker, two databases, contracts to version
  • Eventual consistency between services, so retries and dead letters must be designed
  • Shared mechanics need a home — they live in versioned libraries, not copied code

System at a glance

Simplified. Clients reach one entry point; two domain services each own their data and meet only on the event bus.

Patterns in use

Each one is in the code today, not on a wish list.

Database per service

Fleet and Transport operations each own a PostgreSQL database. Data crosses a boundary only through an API or an event.

BFF without a database

The backoffice gets one entry point that composes the domain services for its screens. It stores nothing, and every call it makes has a time budget.

Transactional outbox

An integration event is saved in the same transaction as the change that caused it, then published. No change without its event, no event without its change.

Aggregates and domain events

State-stored aggregates guard the rules and raise events. Deliberately no event sourcing and no full CQRS — the outbox gives what is needed.

Retries and dead letters

Each consumer owns its durable on the publisher's stream. A message that fails every delivery is parked on a dead-letter subject, not dropped.

One trace across the bus

W3C trace context travels on the message headers, so a request and the events it causes show up as one trace.

Contracts first, clients generated

Every API publishes OpenAPI; clients are generated — Kiota for .NET, Orval for the React app — and published as packages. Events are described in AsyncAPI.

Shared libraries, one way per mechanism

Messaging, tracing and health reporting live once, in versioned NuGet packages every service consumes — no copy-paste between services.

A service template

New services start from a template with the layers, health reporting and telemetry already in place, so every service looks and runs the same way.

The product

Taken from the mock build, which runs on fixtures with no backend. Values no endpoint serves yet are tagged MOCK on purpose: a build is either mock or real, never both, and a real build cannot show a mock value.

What proves it works

Tests at every level

  1. Unit and integration tests in every service
  2. Architecture tests guard the layers
  3. Browser tests run the backoffice against fixtures and against the test environment
  4. k6 load tests in the build pipeline

A simulator as a real user

  1. Seeds a network, then starts trips and drives vehicles along their routes
  2. Talks only to the public APIs — no back door into a database
  3. Vehicles report positions continuously: real load the platform has to carry
