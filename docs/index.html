Self-hosted · cloud native, at home

Everything around the application.

MRZ is a self-hosted, cloud-native platform, built almost entirely on open-source and free software, that covers the whole delivery chain — planning, building, running, securing and observing software. It is built to carry products, not one app: everything a product needs around its code is already in place, so a new product starts from the template and plugs in. TM, a transit-management product, is the first one and the proof that it works. More are meant to follow.

One box

Everything on this page — CI server and agents, NATS clusters, databases, the whole observability stack, the apps — runs on a single Linux machine. It carries more than 60 containers, and it is still fast. No VM layers in between: Linux and Docker. And it starts itself: power the host on, and Docker brings every tier back up, from the CI server to the apps, with no hands on the keyboard.

The pillars

Seven pillars. The first six are the platform every product gets; the seventh is the first product on it, and it keeps the platform honest.

01

Plan & code

Where work is decided and written down before it is built.

  • GitHub
  • YouTrack
  • Architecture in Git

Every decision is written down with its reasons and its date, and every shortcut with the condition that ends it, so any "why is it like this?" can be looked up, not remembered. The whole architecture lives in its own repo, as Markdown next to the code: the spec and its diagrams, decisions (ADRs), standards, feature notes and the design system. An AI agent team does much of the work under the same written rules; a person reviews it and commits.

02

Build & release

From commit to versioned artifact, with secrets kept out of the repo.

  • TeamCity
  • 3 agents
  • Docker Registry
  • Gitea NuGet + npm feeds
  • Infisical · secrets

Each service publishes its typed API client as a NuGet package, and the BFF its TypeScript client as an npm package; consumers pin versions, so a contract change is a reviewed commit. Secrets live in Infisical and are injected at runtime, never written into a repo or an image.

How it works
03

Deploy: GitOps lite

Git records exactly what runs in each environment, so a deploy can be seen, repeated and rolled back.

  • Deploy repo
  • Pinned image tags
  • Docker Compose
  • Bash scripts
  • TeamCity-driven

Every successful deploy ends in a commit that pins the new version — the history of that file is the history of what was live. Migrations run gated first; then only the services whose image changed are replaced in place, the rest are left untouched. Prod is set up to take test's image tag, never a rebuild; test is where TM runs today. Since November 2026 a push deploys a service to test by itself: the deploy waits for the green build, and only that service's own repo can start it, so the deploy repo's commits never set off another deploy. Self-healing reconcile from Git is built and waiting to be switched on.

How it works
04

Run

The application platform: storage, messaging, isolation.

  • Docker
  • PostgreSQL
  • NATS JetStream
  • 3-node NATS cluster per environment
  • Test and prod kept apart
  • Portainer

Every tier and environment has its own Docker network; test and prod each get their own NATS cluster and database. Portainer is the quick way in: a container, its setup and its logs.

How it works: when something falls over
05

Secure access

One front door, one identity provider.

  • Traefik
  • oauth2-proxy
  • Keycloak SSO
  • ngrok · temporary

Traefik is the front door and Keycloak the single sign-on behind it: a tool that speaks OIDC signs in with Keycloak directly, the rest through oauth2-proxy, and the TM app signs in with Keycloak directly too (OIDC with PKCE) while its BFF validates every token. ngrok is a temporary tunnel to reach the box, and it is meant to go. Databases and brokers are never exposed.

Observe

Logs, traces, metrics and uptime — OpenTelemetry wherever it is available.

  • Prometheus
  • Grafana
  • Jaeger + Elasticsearch
  • Seq

A service doesn't ship without logs, traces and metrics: the template and the shared libraries give it all three. Observability joins every network to scrape, so no metrics port is opened on the host.

How a request travels

A user opening the TM backoffice, end to end.

  1. Internet
  2. ngroktemporary
  3. Traefikroutes by host and path
  4. Keycloaksign-in · OIDC + PKCE
  5. TM frontend + BFFchecks the token · composes views
  6. Fleet · Transport opsown data, own rules
  7. PostgreSQL · NATSnever exposed
Watching every hop traces → Jaegerlogs → Seqmetrics → Prometheus → Grafanahealth → Uptime Kuma

Commit to running container

  1. Push to GitHub
  2. TeamCity builds and tests
  3. API client packed → Gitea feed; image → Docker Registry
  4. Test deploy starts by itself once the build is green: migrations first, gated — a failure keeps the last good version
  5. Changed services replaced in place, secrets injected from Infisical at runtime
  6. The new version is pinned in the deploy repo — Git now says what is live

An event through the system

  1. A vehicle is decommissioned in Fleet
  2. Fleet stores the change and its event in one transaction, then publishes it to NATS JetStream
  3. Transport ops reads it through its durable consumer and cancels the vehicle's running trip
  4. Each service keeps its own PostgreSQL database — neither reads the other's
  5. Visible as one trace across both services

How components get in

Criteria

  • Self-hosted in containers — Docker today, Kubernetes-compatible tomorrow
  • Open source or free for small teams
  • Easy to set up and well documented
  • Integrates with the rest of the chain
  • Standard protocols — OpenTelemetry, OIDC
  • Can cluster when it needs to scale
  • Application-facing tools must have a solid .NET library

Selection process

  1. Name the problem it solves
  2. Find candidates: the CNCF and CD Foundation landscapes, or an article worth a try
  3. Follow the project's own deployment guide
  4. Check it against the criteria
  5. Compare alternatives
  6. Script a self-hosted setup
  7. Experiment — then keep it or retire it
