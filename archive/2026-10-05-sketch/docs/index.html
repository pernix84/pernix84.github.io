Everything around the application.

MRZ is a self-hosted, cloud-native platform that covers the whole delivery chain — planning, building, running, securing and observing software. The goal is not an app, it is the machinery every app needs. TM, a transit-management product, runs on it as the proof.

  • 1 Linux host
  • 5 tiers
  • 2 app environments
  • 1 real workload
One box

Everything on this page — CI server and agents, NATS clusters, databases, the whole observability stack, the apps — runs on a single Linux machine. It is already carrying a lot of containers, and it is still fast. No VM layers in between: Linux and Docker.

The pillars

Seven pillars. The first six are the platform; the seventh is what keeps it honest.

01

Plan & code

Where work is decided and written down before it is built.

  • GitHub
  • YouTrack
  • ADRs in Git

Architecture decisions, feature notes and standards live as Markdown next to the code.

02

Build & release

From commit to versioned artifact, with secrets kept out of the repo.

  • TeamCity
  • 3 agents · 1 CUDA
  • Docker Registry
  • Gitea NuGet feed
  • Infisical

Each service publishes its typed API client as a NuGet package; consumers pin versions, so a contract change is a reviewed commit.

03

Deploy: GitOps lite

Git records exactly what runs in each environment, so a deploy can be seen, repeated and rolled back.

  • Deploy repo
  • Pinned image tags
  • Docker Compose
  • Bash scripts
  • TeamCity-driven

Every deploy ends in a commit that pins the new version — the history of that file is the history of what was live. Migrations run gated before a zero-downtime rolling replace; prod gets the same image tag as test, never a rebuild. Self-healing reconcile from Git is built and waiting to be switched on.

04

Run

The application platform: storage, messaging, isolation.

  • Docker
  • PostgreSQL
  • NATS JetStream
  • 3-node clusters
  • test / prod

Every tier and environment has its own Docker network; test and prod each get their own NATS cluster and database.

05

Secure access

One front door, one identity provider.

  • Traefik
  • oauth2-proxy
  • Keycloak SSO
  • ngrok · temporary, dev only

Traefik is the front door and Keycloak the single sign-on behind it. ngrok is only a temporary, development-time tunnel to reach the box — it lands on Traefik, never on a service port, and it is meant to go. Databases and brokers are never exposed.

06

Observe

Logs, traces, metrics and uptime — OpenTelemetry wherever it is available.

  • Prometheus
  • Grafana
  • Jaeger + Elasticsearch
  • Seq
  • Uptime Kuma
  • cAdvisor
  • NATS Surveyor

Observability joins every network to scrape, so no metrics port is opened on the host.

07

Prove it: TM

A transit-management product built on the platform — not a hello-world.

  • .NET 10
  • Fleet service
  • Transport ops service
  • Backoffice BFF
  • React backoffice

Two domain services, each owning its database, talking over NATS; a BFF composes them for the UI and publishes the OpenAPI contract the frontend generates its client from.

Commit to running container

  1. Push to GitHub
  2. TeamCity builds and tests
  3. API client packed → Gitea feed; image → Docker Registry
  4. Deploy: migrations first, gated — a failure keeps the last good version
  5. Rolling replace, secrets injected from Infisical at runtime
  6. The new version is pinned in the deploy repo — Git now says what is live

An event through the system

  1. A vehicle is registered in Fleet
  2. Fleet stores it and publishes an event to NATS JetStream
  3. Transport ops reads it through a durable consumer
  4. Each service keeps its own PostgreSQL — neither reads the other's
  5. Visible as one trace across both services

How components get in

Criteria

  • Self-hosted in containers — Docker today, Kubernetes-compatible tomorrow
  • Open source or free for small teams
  • Easy to set up and well documented
  • Integrates with the rest of the chain
  • Standard protocols — OpenTelemetry, OIDC
  • Can cluster when it needs to scale
  • Application-facing tools must have a solid .NET library

Selection process

  1. Name the problem it solves
  2. Search the CNCF and CD Foundation landscapes
  3. Follow the project's own deployment guide
  4. Check it against the criteria
  5. Compare alternatives
  6. Script a self-hosted setup
  7. Experiment — then keep it or retire it
